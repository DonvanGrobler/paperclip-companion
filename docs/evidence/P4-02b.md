## Scope and test-first evidence

Add an unwired main helper using jose's actual signature/claim verification with
trusted normalized public snapshots. No production entry/preload/renderer imports
it. No network resolver, key URL, credential file, provider request or new IPC.
Only a five-field immutable validated identity projection escapes success;
failures return null. Snapshot replacement, abort and disposal reject stale
crypto results. The transaction still owns state/replay/account/commit authority.

- Initial typed no-op contract: **3 failed / 5 passed** (valid signature,
  rotation and transaction installation fail); this was behavioral red evidence,
  not a missing-module/compile failure. Implemented the helper: all 8 passed.
- Expanded independent crypto/negative suite: **147 passed**, including signed
  claim denials, tampering, HMAC/public-key confusion, forbidden header keys/URLs,
  invalid snapshots, timing, rotation, cancellation and transaction composition.
- Added inherited-parameter hardening case: **1 failed / 148 skipped** because a
  polluted prototype could supply a missing snapshot field. Required own root
  and mandatory key fields; the regression now passes.
- Final suite: **149 passed**. OpenSSL/Node crypto signs ephemeral fixtures;
  the maintained library verifies them. Actual RSA 2048- and 4096-bit signatures
  pass; an actual 1024-bit key is rejected. Fixtures/private keys/JWTs are never
  saved, logged, snapshotted or included in assertion dumps.
- Source coverage: **100% statements / branches / functions / lines** for the
  new helper (128/128 branch outcomes). This measures our wrapper, not an audit
  or full code coverage of the third-party library.

Composition tests run the existing transaction with real verifier plus fake
exchange/store. A valid ID-only result reaches fake installation without enabling
inference; a bad signature or nonce reaches no prepare/commit. No injected fake
signature-success result substitutes for the actual crypto checks in this slice.

## Source review, limits and next

Primary sources read on 27 October: official OpenAI
[OSS sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in)
and [ID-token verification](https://developers.openai.com/siwc/website),
[OIDC Core 3.1.3.7](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation),
[RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html), and pinned
[jose APIs](https://github.com/panva/jose/tree/v6.2.13/docs).
The ADR distinguishes normative identity/algorithm checks from our provisional
RS256/single-audience/key/size/age policy. No live metadata or account proves
that local profile compatible with actual OpenAI signing configuration.

Trusted synthetic keys establish crypto behavior, not issuer provenance. A
future trusted discovery/TLS/destination/key-cache loader must own that boundary,
including unknown-kid refresh. No arbitrary renderer/token-supplied snapshot may
be used. The helper is not a complete OAuth/OIDC/session client, replay barrier,
account/inference grant or native Windows crypto/storage integration. Native
crypto may finish after abort; stale output is discarded, memory erasure unproved.

Next smallest: P4-02c protected Windows credential staging/commit and restart
with synthetic secrets. Trusted key loading, registration retry hints,
refresh/logout, real account/browser/provider wiring, notices and actual P4-05
human testing remain separate. Human review #79 stays Backlog, OD-04 proposed,
G1–G4 and OD-02 open. No account/service acceptance or phase promotion inferred.
