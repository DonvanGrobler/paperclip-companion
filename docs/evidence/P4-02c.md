## Scope and test-first evidence

The main-only store accepts the native Windows async encryption capability and a
trusted absolute private directory. It validates/copies a bounded versioned
record, encrypts before any file write, exclusively stages and flushes ciphertext and
returns the existing transaction's synchronous atomic commit/discard contract.
It reads only the installed file after restart, never an orphan. No production
entry point/preload/renderer imports the store. No dependency, IPC, network,
provider, screenshot, settings or workflow change.

Initial typed no-op contract: **7 failed / 0 passed**, covering genuine
encrypt/stage/commit/restart, cancellation, unavailable OS encryption, unsupported
platforms, interrupted staging and corruption. Implemented minimum: **7 passed**.
Expanded negative/race/filesystem suite covers schema and encoded size bounds,
own fields/accessors, identity-only grants, input copying, delayed native work,
abort/disposal/overlap, native errors, actual replacement and injected write,
flush, close and rename failures that preserve the installed bytes. It also
checks bounded reads/type/size changes, key-rotation advice without writes and
composition with the existing sign-in transaction.

Unit encryption is an **ephemeral AES-GCM test double**, not DPAPI verification.
Tests use actual temporary files and never write plaintext token fixtures. Keys
are generated per test and released; assertions inspect booleans/statuses or
counts rather than token values. Fake native errors are private and fixed public
outcomes are checked. No snapshots, console diagnostics or live provider calls.

The explicit Windows Electron test builds only this helper into a temporary
test bundle and launches six processes against the same temporary profile/store:
install; leave an uncommitted encrypted stage; restart and restore the original;
cancel then atomically replace; restart and restore the replacement; deny actual
corruption. Native OS safeStorage is used, without a crypto-success fake.
Synthetic markers are derived only inside the test main process, never returned
through evaluation. Results are booleans; no renderer/window, token IPC, trace,
video, screenshot, artifact upload or real account is involved. Process restart
is not machine crash/power-loss verification.

## Security, licensing and remaining work

Pinned Electron docs, Node fs API/Windows source and Microsoft replacement
semantics were rechecked on 27 October; hashes/links and assumptions are in ADR 0032. The OS provider protects data at rest from other users, not same-user
programs. Require a trusted private local directory and single owner; reject
unsupported OS/encryption without fallback. No plaintext credentials or raw
native/provider exceptions enter settings, logs, UI or snapshots.

One same-directory synchronous rename installs the file; no pre-delete, async
late install or post-rename fallible filesystem operation. Failure preserves the
previous record. Abort/disposal removes only staging; it is not logout or
installed credential deletion. Cleanup failures/process termination can leave
encrypted orphans that are ignored. No claims about power-loss durability,
secure erasure, filesystem rollback, arbitrary filesystems, multiprocess locking
or unmeasured main-thread staging latency. Restored data is not a fresh session,
verified identity, inference grant or consent; no automatic provider call follows.

No package/version/license/asset change or DevKit implementation reuse. Source
license remains UNLICENSED; proposed auth choices/OD-04 and human review #79
remain open. Earlier G1–G4/OD-02 blockers and unchanged intent recall limitation
remain explicit. Production auth/capture remain disabled; actual P4-05 account
and protected restart evidence is outstanding.

Next smallest: trusted discovery/JWKS loader and bounded cache under a reviewed
